# Daily Game Preset Routine — Design

Date: 2026-08-14
Status: Approved pending spec review

## Goal

Make the repository able to absorb one new game preset per day, generated by a scheduled
Claude session, without degrading as the count climbs. The routine itself is scheduled
outside this repository; what ships here is everything it needs to land a preset safely
and mechanically, plus the guard rails that decide whether the preset it invented is
allowed to exist.

Four things break the moment a preset a day starts arriving, and all four are cheap to
fix now and expensive to fix at preset ninety.

**`PresetId` is a closed union.** `packages/engine/src/presets.ts` declares
`'pact' | 'tiers' | 'pact-blitz' | 'tiers-v2'`, so every daily preset is a type edit in
addition to a data edit — and `packages/server/src/testing.ts` imports the union.

**`presets.test.ts` asserts the exact list.** Its first line is
`expect(PRESETS.map((p) => p.id)).toEqual([...])` over four hard-coded ids. Every daily
run would begin by turning the suite red and end by editing the assertion that was
supposed to be checking it — which is how a test stops being a test.

**The home page renders `PRESETS.map(...)` into a grid.** Four cards is a menu. Thirty
cards is a wall, and three hundred and sixty-five is a denial of service against the
person trying to start a game.

**Nothing says a new preset is any good.** There is no bound on turn cap or turn length
that a preset must respect, no check that it differs from the ones already shipped, and
nothing preventing a generated `neutralGarrisonDelta: -40`. A generator with no gate
produces a catalogue of near-duplicates and unplayable outliers.

The change is a dated catalogue, an invariant suite that validates any preset rather than
recognising four specific ones, a home page that features one preset a day instead of all
of them, and a `/daily-preset` command holding the routine's instructions.

## Decisions (settled during brainstorming)

| Question                                   | Decision                                                                                                                                                                                |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Where does a generated preset live?        | Appended to `PRESETS` in `packages/engine/src/presets.ts`, as source. The catalogue is append-only.                                                                                     |
| How does the home page stay a menu?        | `GamePreset` gains `featuredOn?: string`, an ISO date. A preset with one is a daily and is carded on that date only; a preset without one is evergreen and always carded.               |
| Whose "today"?                             | UTC, on both ends. The routine stamps a UTC date and the client reads `toISOString()`, so every player sees the same preset of the day regardless of timezone.                          |
| Are yesterday's presets still playable?    | Yes. `presetById` resolves every preset forever; only the card goes away. Games created under a daily keep resolving, and their `presetName` keeps rendering.                           |
| Does `PresetId` stay a union?              | No — it becomes `string`. Tomorrow's id is not knowable at compile time, and a union nobody can complete is a union that lies.                                                          |
| What stops an unplayable generated preset? | `presets.test.ts` becomes a validator: bounds on every field, run over every entry in `PRESETS`. It is written so that adding a preset that breaks it is what turns CI red.             |
| What stops a boring near-duplicate?        | The same suite rejects two presets sharing a tuning tuple. Novelty is a gate, not a hope.                                                                                               |
| Where do the turn-length bounds live?      | Moved from `packages/server/src/games.ts` into the engine's `constants.ts`. The preset validator has to check the real bound, and a bound copied into two files is a bound that drifts. |
| Does the routine get new tuning knobs?     | No. It composes the seven fields `GamePreset` already has. A generator that can add knobs can add unreviewed mechanics daily.                                                           |
| How does the routine know it worked?       | `pnpm sim -- --preset <id>` — the balance harness already takes a preset id and exits non-zero on a failed gate.                                                                        |
| Push to `main` or open a pull request?     | Draft pull request, per day, per this repo's normal flow. Nothing generated merges itself.                                                                                              |
| Does CI gain a per-preset balance sweep?   | No. CI's 800-game sweep stays on the legacy tuning it was calibrated against; per-preset simulation is the routine's job, at generation time, recorded in the pull request body.        |
| Is a preset seeded as part of this change? | Yes, one — produced by running the new command. It gives the featured path a caller and a test, and proves the routine end to end rather than asserting it would work.                  |

**Rejected:** presets as JSON or Firestore documents (a runtime loader plus runtime
validation, to avoid a code change that was going to be a code change anyway — and it
would put unreviewed game rules in production without a diff); one file per preset under
`presets/` with a barrel (three hundred and sixty-five files a year, and the barrel is the
same append-only list with more ceremony); deleting dailies after a week (finished games
store `presetId`, and a deleted preset means a game whose mode has no name); an archive
page listing every past daily (a browse surface for a catalogue that does not exist yet —
`## Out of scope`); ranking or rating presets to pick which to feature (telemetry the game
does not collect, in service of a decision the date already makes).

## Engine

`GamePreset` gains one optional field:

```ts
export interface GamePreset {
  // ...existing fields...
  /** ISO date (UTC) this preset is the preset of the day; absent means evergreen. */
  featuredOn?: string;
}
```

`PresetId` widens to `string`. It stays exported and stays used — `presetId` fields across
the server read better named than as a bare `string` — but it stops claiming to enumerate
anything.

One new selector, pure and clock-free like everything else in the engine:

```ts
/** What the home page offers on a given UTC date: the evergreens, plus that day's daily. */
export function presetsForDate(isoDate: string): GamePreset[] {
  return PRESETS.filter((p) => p.featuredOn === undefined || p.featuredOn === isoDate);
}
```

Array order carries the ordering — evergreens first because they are at the top of the
array, the daily last because the routine appends. No sort, no featured/archive split, no
second array to keep in step.

`MIN_TURN_MINUTES` and `MAX_TURN_MINUTES` (5 and 10 080) move from `games.ts` into
`constants.ts` beside `MIN_TURN_CAP`/`MAX_TURN_CAP`, and the server imports them. They are
creation-time bounds on a configurable game, which is what that block of constants is;
they were local to the server only because that is where the config endpoint was written.

Nothing else in the engine changes. `presetById`, `presetRules` and the rules layering are
untouched — a daily preset is an ordinary preset that happens to carry a date.

## Web

`Home` calls `presetsForDate(new Date(now).toISOString().slice(0, 10))` instead of mapping
`PRESETS` directly. It already holds `now` from `useNow()`, so the grid rolls over at UTC
midnight without a reload. The daily card carries a "Preset of the day" pill; the
evergreens are unchanged.

No other web surface changes. `GameSetup` looks presets up by id and does not care whether
one is dated, and a game created from yesterday's daily still names its preset correctly
because the catalogue never forgets.

## The routine

`.claude/commands/daily-preset.md`, invoked by a scheduled session as `/daily-preset`:
branch `preset/<YYYY-MM-DD>`, read the catalogue, compose a preset that no existing tuning
tuple matches, append it with today's UTC date, simulate it, run the gate, commit, push,
open a draft pull request carrying the simulation numbers.

Its hard rules are what keep a daily generator from becoming a daily refactor: do not add
fields to `GamePreset`, do not edit an existing preset, do not touch anything outside
`presets.ts`, one preset per run, and if the balance gates fail, retune within bounds and
re-simulate rather than removing the gate. `CLAUDE.md` gains the branch convention and a
pointer.

The schedule itself is not in this repository. The command documents the cron and the
prompt to give it, and someone creates it.

## Testing

`presets.test.ts` is rewritten around a local `problemsWith(preset, all)` returning a list
of strings, run over every entry in `PRESETS`:

- id is unique, non-empty, kebab-case; name and tagline are non-empty; the tagline fits a
  card (≤ 64 characters)
- `defaultTurnCap` within `[MIN_TURN_CAP, MAX_TURN_CAP]`, `defaultTurnMinutes` within
  `[MIN_TURN_MINUTES, MAX_TURN_MINUTES]`, both integers
- `warEconomyInterval` ≥ 1, `neutralGarrisonDelta` within `[-3, 0]`, `plunderIncome` within
  `[0, 3]` — the ranges the shipped presets already occupy, with `-3` noted in `presets.ts`
  as indistinguishable from `-2` because garrisons floor at 1
- `contest` and `tiersPayout` are legal values
- `featuredOn`, when present, is `YYYY-MM-DD` and unique across the catalogue
- no two presets share a tuning tuple

The suite then runs the same validator over deliberately malformed presets and asserts it
catches each class of defect, so the guard rail is demonstrably live rather than
vacuously green. The four evergreens keep their existing exact-value regression test —
what goes away is the assertion that the catalogue has exactly four entries.

`presetsForDate` gets its own cases: evergreens always, today's daily on its date and not
the day before, and no daily at all on a date nobody generated for. `Home.test.tsx` gains a
case for the pill.

## Out of scope for v1

- An archive page for browsing past dailies. Presets stay creatable by id; nothing lists
  them.
- Auto-merging the daily pull request.
- A per-preset balance sweep in CI. The routine simulates; CI keeps its calibrated run.
- New tuning knobs on `GamePreset`, and any mechanic a preset could turn on that a preset
  cannot turn on today.
- Scheduling the routine, and any repository-side record of whether it ran.
- Switching a lobby game from one preset to another (already out of scope in the presets
  spec, and dailies do not change that).
